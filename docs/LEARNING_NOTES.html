Module 0 — Foundations

Concept 01

What a large language model actually does

An LLM is a function that takes a sequence of tokens and returns a probability distribution over the next token. That is the whole mechanism. Text generation is that function called repeatedly, each output appended to the input.

  • Token — a sub-word unit, roughly 4 characters of English. “Diversification” might be 3 tokens. Pricing, limits and context windows are all measured in tokens, never words.
  • Context window — the maximum number of tokens the model can attend to in one call. GPT-4o has 128,000 — roughly a 300-page book — but it is a hard budget shared between system prompt, retrieved context, conversation history and the answer, and you pay for every token of it on every single call.
  • Temperature — scales the distribution before sampling. 0 is near-deterministic (pick the most likely token); 1.0 is more varied. For a finance assistant, run low: 0.1–0.3.
  • Top-p (nucleus sampling) — restricts sampling to the smallest set of tokens whose cumulative probability exceeds p. An alternative knob to temperature; tune one, not both.
  • Stateless — the model remembers nothing between calls. Every “memory” feature in this project is us re-sending history.
Why this matters hereBecause the model is a next-token predictor with no notion of truth, accuracy must be engineered around it: retrieval for facts, Python for arithmetic, prompts for boundaries. That single realisation is what the whole architecture is for.
Interview grill
Why does an LLM hallucinate?

Because it optimises for plausible next tokens, not for truth. It has no internal mechanism that distinguishes a fact it memorised during training from a fluent continuation that merely fits the pattern. Low-frequency facts — a specific expense ratio, yesterday's closing price — are exactly where the pattern is strong and the memory is weak, so it generates confidently and wrongly.

Your users ask about today's stock prices. Why can the model not simply know them?

Two reasons. The weights are frozen at training time, so anything after the cutoff was never seen. And even for in-window data, there is no retrieval step — the model cannot look anything up unless we give it a tool. Hence the market-data layer in Phase 6: prices come from an API, and the model only narrates them.

Why GPT-4o, and not Gemini or Claude?

Two things drove it. The router is a structured-output problem — I need a reliable JSON classification on every turn — and GPT-4o's structured outputs and function calling are the most dependable I tested for that; a router that occasionally returns prose instead of a label poisons the entire graph. Second, ecosystem: LangGraph's OpenAI integration is the best-trodden path, so I spend my time on architecture rather than adapter bugs.

The cost against it is real and I would name it: Gemini 2.0 Flash has a free tier and a far larger context window, so for a pure high-volume RAG workload it would be cheaper. I mitigated that with model tiering — gpt-4o-mini classifies, GPT-4o writes — which removes most of the per-turn cost, since routing is the only call that happens on literally every turn. And because every model call goes through one interface, switching provider is one adapter class, not a refactor. That seam is the actual engineering answer.

What temperature did you use and why?

0.2 for every agent. Financial education rewards consistency and penalises creative variation; two users asking the same question should get substantially the same explanation. I kept it non-zero only because a hard 0 makes phrasing feel mechanical across a multi-turn conversation.

Concept 02

Prompt, chain, agent, workflow

These four words get used interchangeably and they are not the same thing. Being precise here is half of sounding senior in an interview.

TermDefinitionWho decides the control flow
PromptOne call: input in, text out.Nobody — there is no flow.
ChainA fixed pipeline of calls. A → B → C, always.You, at code-writing time.
AgentAn LLM in a loop with tools: it decides what to call, observes the result, decides again, stops when done.The model, at runtime.
Workflow / graphNodes with explicit edges and shared state. Some edges are conditional, decided by the model; the topology is yours.Split — you own the topology, the model owns the branch choices.

Finnie is a workflow of agents: LangGraph owns the shape, the router node lets the model pick the branch, and each agent node is itself a small bounded agent. That is deliberately less autonomous than a free-running ReAct agent — and in a regulated domain, less autonomy is a feature, not a limitation.

Interview grill
Why a graph instead of a single ReAct agent with six tools?

Three reasons I can defend. Testability — I can unit-test the router independently of the agents, and assert which node ran. Bounded context — each node gets only the prompt and state it needs, rather than one giant system prompt describing six domains. Predictability — a free-running agent can loop, re-call tools and run up cost unboundedly; a graph has a finite, inspectable set of paths, which matters when every answer is user-facing financial content.

The trade-off is honest: a single agent would handle a genuinely novel query shape more gracefully. I accepted less flexibility for more control.

When would you choose CrewAI over LangGraph?

When the task is naturally collaborative and loosely specified — a research crew where a writer, critic and editor iterate and the number of rounds is not known in advance. CrewAI's role-and-task abstraction expresses that in very little code. I chose LangGraph because my routing is a classification problem with a known set of destinations, and I wanted explicit state I could checkpoint and assert on.

Concept 03

Why multiple agents at all

The honest answer is not “because it is more powerful”. One model with one long prompt can, in principle, do all six jobs. We split it for engineering reasons:

  1. Prompt focus. A system prompt that says “you explain tax and read portfolios and summarise news” dilutes instruction-following. Each extra concern measurably degrades adherence to the others.
  2. Context budget. Only the portfolio agent needs holdings data; only the Q&A agent needs retrieved articles. Narrow nodes keep each call cheap and focused.
  3. Separation of concerns. The rubric's own phrase. Portfolio maths changes for different reasons than news summarisation; they should be different files with different tests.
  4. Independent evaluation. I can measure retrieval quality on the Q&A agent without market data confounding it.
  5. Graceful failure. If the news source dies, five agents keep working.
The trapDo not claim multi-agent systems are smarter. They are not — it is the same model behind every node. They are more maintainable, testable and debuggable. Say that and you sound like an engineer; say “smarter” and you sound like a brochure.
Interview grill
Isn't six agents over-engineering for this?

For a weekend prototype, yes. The justification is the shape of the domain: six genuinely distinct capabilities, with different data dependencies — RAG, live prices, pure maths, external news. Those are natural seams. I would push back on splitting further; splitting the Q&A agent by asset class, for instance, would be arbitrary, because every one of those would need the identical pipeline and prompt.

How do your agents communicate?

They don't talk to each other directly — that is deliberate. They communicate only through shared graph state: each node reads what it needs and appends an AgentResult. Direct agent-to-agent calls create an implicit call graph nobody can see, plus cycle risk. With a central state object and a supervisor topology, the full conversation is one inspectable dict I can log, checkpoint and assert against.

Concept 04

RAG — and why not fine-tuning

Retrieval-Augmented Generation: before answering, fetch relevant documents and place them in the prompt, so the model's answer is grounded in text you control rather than in frozen weights.

The distinction underneath it:

  • Parametric knowledge — baked into the weights. Fast, free at inference, impossible to audit, impossible to update without retraining, and silently wrong at the edges.
  • Non-parametric knowledge — sits in an external store. Costs retrieval latency and prompt tokens, but is updatable, auditable and citable.

Finance needs the second kind. Content changes, every claim should be traceable, and “the model said so” is not an acceptable provenance for financial education.

Interview grill
Why RAG rather than fine-tuning on your 100 articles?

Four reasons. Citations — RAG hands me the source document, which the rubric and the compliance story both require, and fine-tuning cannot. Freshness — new content means re-indexing, not retraining. Volume — 100 articles is far below what meaningfully moves weights; I would mostly get stylistic drift, not knowledge. And auditability — when an answer is wrong I can inspect exactly which chunks were retrieved, which is the difference between a debuggable system and a black box.

I would consider fine-tuning for something else entirely: enforcing a house explanation style across every response. That is form, not facts.

GPT-4o takes 128k tokens. Why not just paste all 100 articles into every prompt?

They would not fit — 100 articles is well past 128k — but suppose they did. Cost scales linearly with input tokens, so every trivial question would pay for the whole corpus; on GPT-4o pricing that turns a fraction-of-a-cent question into a few cents, multiplied by every turn of every conversation. Latency rises with context length. And accuracy actually degrades — the lost-in-the-middle effect means relevant text buried in a huge context is attended to less reliably than the same text in a short, targeted one. Retrieval is also what gives me citations and a relevance threshold; a dump gives me neither.

Concept 05

Embeddings and vector search

An embedding model maps text to a fixed-length vector — 384 numbers for all-MiniLM-L6-v2 — positioned so that semantically similar text lands nearby. “How do I spread my risk?” and “diversification basics” share almost no keywords but sit close together in that space. That is the entire reason RAG beats keyword search for natural-language questions.

Cosine similarity measures the angle between two vectors, ignoring magnitude. It runs from −1 to 1; for retrieval you are looking at roughly 0.3 to 0.9. The practical trick: normalise every vector to unit length first, and then the dot product is the cosine. That is why we use FAISS's IndexFlatIP (inner product) rather than IndexFlatL2 (Euclidean) — with normalised vectors, inner product gives cosine for free.

import numpy as np, faiss
vecs = model.encode(chunks)                 # (n, 384) float32
faiss.normalize_L2(vecs)                    # unit length, in place
index = faiss.IndexFlatIP(384)              # exact inner-product search
index.add(vecs)

qv = model.encode(["what is an expense ratio"])
faiss.normalize_L2(qv)
scores, ids = index.search(qv, k=5)         # scores are now cosines

The index stores only vectors and integer ids. The text and metadata live in a parallel list or JSON file, keyed by the same id. Keeping them separate is standard practice — it keeps the index small and lets you change metadata without re-embedding.

Interview grill
FAISS versus Chroma versus Pinecone — why FAISS?

FAISS is a library, not a database: in-process, no server, no network hop, and it persists as a single file. For roughly 500–1500 chunks that is strictly the right answer; a flat index searches exhaustively in under a millisecond. Chroma adds a metadata-filtering query layer and a server mode, which I did not need because my metadata store is a dict. Pinecone is a hosted service — it earns its cost at millions of vectors with multi-tenant isolation and no ops team, which describes none of this project. Choosing Pinecone here would be paying for a distributed system to search a thousand rows.

When would a flat index stop being the right choice?

Flat search is O(n · d) per query. At a thousand chunks that is nothing. Somewhere around a hundred thousand to a million vectors, latency becomes visible and you move to an approximate index — IVFFlat, which clusters vectors and searches only the nearest few clusters, or HNSW, a navigable small-world graph. Both trade exact recall for speed, and both need tuning (nprobe, efSearch). The honest framing: ANN is a recall-for-latency trade you should only take once you have measured a latency problem.

Why local embeddings rather than an embedding API?

Indexing is a bulk operation — a thousand-plus chunks in one pass. Through an API that is a thousand billable calls against a rate limit; locally MiniLM does it on CPU in seconds for free, and query-time embedding adds only a few milliseconds. The constraint to respect is that the query must be embedded by the exact same model as the corpus, since two models' vector spaces are unrelated. Changing the embedding model means a full re-index — no exceptions.

Concept 06

Chunking — the decision that quietly determines RAG quality

You cannot embed a whole article usefully: one vector averaging twelve topics is close to nothing in particular. So documents get split. How you split is the highest-leverage knob in the whole pipeline.

  • Too small (one sentence) — precise matching, but the retrieved fragment lacks the context needed to answer, and pronouns dangle.
  • Too large (whole article) — rich context, but the embedding is diluted and you waste prompt tokens on irrelevant paragraphs.
  • Overlap — repeating 10–20% of adjacent text across chunk boundaries, so an idea split across a boundary still appears whole in at least one chunk.
  • Structure-aware — split on Markdown headings first, then by size within a section. A heading is an author-provided semantic boundary; using it beats any character count.

Our starting point: split on ## headings, then subdivide anything over ~800 characters with ~100 characters of overlap, and prepend the article title and heading to each chunk's text before embedding so an isolated chunk still carries its topic.

Interview grill
How did you choose your chunk size?

Empirically, not from a blog post. I built a set of twenty representative questions with the answer I expected, then compared retrieval at a few configurations and looked at whether the correct chunk appeared in the top three and whether it contained enough context to stand alone. Heading-aware splitting at around 800 characters with 100 of overlap won. The point I would make in an interview is that chunk size is a function of your documents' structure — dense reference material wants smaller chunks than narrative prose — so it has to be measured per corpus.

What breaks if you have no overlap?

Any idea that straddles a boundary is now half in one chunk and half in another, and neither half answers the question. Classic case: a definition at the end of one chunk whose worked example starts the next — retrieve either and the user gets half an explanation. Overlap is cheap insurance; the cost is a slightly larger index and occasional near-duplicate hits, which deduplication on source offset handles.

Concept 07

Tool calling — how an LLM “does” anything

A model cannot call a function. What it can do is emit structured text naming a function and its arguments; your code parses that, executes the real function, and feeds the result back in. The loop is:

1. You send: prompt + JSON schemas of available tools
2. Model returns: {"tool": "get_quote", "args": {"ticker": "AAPL"}}
3. YOUR code runs get_quote("AAPL") -> {"price": 184.2, ...}
4. You send that result back as a tool message
5. Model writes prose using it

Two consequences worth internalising. The tool's description is a prompt — it is the only thing the model uses to decide whether to call it, so vague descriptions cause mis-selection far more often than model weakness does. And step 3 is ordinary code under your control, which is exactly where validation, rate limiting and auth belong: never trust model-supplied arguments.

Where this shows up in FinnieTwice. Inside agents, where the market agent calls the price layer. And in Phase 13, where MCP exposes those same tools to any external client — MCP is a standard protocol for the schema-and-dispatch dance above, so one server works with Claude Desktop and anything else that speaks it.
Interview grill
The model keeps calling the wrong tool. How do you debug it?

I treat it as a prompt bug, not a model bug. First I check the descriptions for overlap — two tools whose descriptions could both plausibly answer the query is the most common cause, and the fix is sharpening the boundary and saying explicitly when not to use each one. Then argument schemas: enums instead of free-form strings, required fields marked. Then I add a couple of examples. If it still mis-routes, I reduce the number of tools visible at that node — which is itself an argument for the graph architecture, because each node only ever sees its own tools.

Concept 08

State, memory and context preservation

The model is stateless, so “memory” is entirely an engineering construct: the set of things you choose to re-send on every turn. There are distinct kinds, and conflating them is a common interview stumble.

  • Short-term / conversational — recent messages, replayed verbatim. Simple and lossless, but grows without bound.
  • Summarised — older turns compressed by the model into a running synopsis. Constant size, lossy, and costs an extra call.
  • Profile / semantic — durable extracted facts: risk tolerance moderate, horizon 15 years, beginner. Small, high value, and the thing that makes guidance feel personal across turns.
  • Checkpointed graph state — LangGraph persisting the whole state object per thread id, so a conversation survives a process restart.

Our policy: keep the last ten messages verbatim, maintain an extracted profile dict, and summarise beyond that window. The rubric scores “context preservation” under Conversational Flow, and the demo case to nail is a pronoun across a domain switch — “is that too risky for me?” three turns after the portfolio was discussed.

Interview grill
A conversation runs 50 turns. What happens?

Naive replay would grow the prompt until cost and latency became unacceptable and the earliest turns pushed context out. So the window is bounded at ten messages; everything older is folded into a running summary, and durable facts are promoted out of the transcript into a profile dict that is always sent and is tiny. The ordering matters: profile first, then summary, then verbatim recent turns — the most important context sits where attention is most reliable.

Why checkpoint graph state at all for a Streamlit app?

Because session_state dies with the browser session and Streamlit re-runs the whole script on every interaction. A checkpointer keyed by thread id means the conversation is durable independently of the UI, which also makes the graph testable on its own — I can resume a thread in a test and assert what the next turn does. It is the difference between memory being a UI feature and memory being a system property.

Concept 09

Education versus advice — the constraint that shapes the prompts

Telling an identified person what to do with their money is regulated activity in essentially every jurisdiction. Explaining how instruments work is not. Finnie must sit firmly on the education side, and that is an architectural requirement, not a footnote.

  • Allowed: “An index fund holds every stock in an index; the usual argument for one is low cost and broad diversification.”
  • Allowed: “Your portfolio is 68% in one holding. Concentration means your outcome depends heavily on a single company.” — an observation with a definition.
  • Not allowed: “You should sell some NVDA and buy a bond fund.” — a personalised recommendation.

How we enforce it in three layers: system prompts that state the boundary and give refusal examples; a disclaimer appended to every user-facing response; and an output-side regex guard for recommendation phrasing that logs and rewrites on a hit. Defence in depth, because a prompt instruction alone is a request, not a guarantee.

Interview grill
How do you stop the model giving financial advice?

I assume prompting will eventually fail and layer accordingly. Prompt level: every agent's system prompt defines the education/advice line and shows how to decline. Output level: a compliance wrapper every response passes through, which appends the disclaimer and pattern-matches recommendation language, logging any hit. Design level: the portfolio agent is built to report metrics and define terms, never to propose target allocations — there is simply no code path that generates a trade suggestion. I would also say plainly that regex is a blunt instrument; it is a safety net under the prompt, not the primary control.

A user asks point blank: “should I buy Tesla?”

The agent declines the recommendation and converts the question into education: it explains what one would look at to evaluate any single stock — concentration risk, the difference between single-stock and diversified exposure, valuation basics — shows the live quote and context, and states that it cannot tell them whether to buy. That is a better product answer as well as the compliant one: the beginner leaves with a framework instead of a verdict.

Concept 10

Virtual environments

Python installs packages globally by default. Two projects that need different versions of the same library then conflict, and one breaks silently. A venv is nothing clever: a private site-packages directory plus a tweaked sys.path. activate merely prepends its Scripts/ to your PATH so python and pip resolve to the local copies.

It matters acutely here because langchain, langgraph and sentence-transformers pin transitive dependencies aggressively. Resolving that inside your system Python is a day you do not get back.

Ranges in requirements, exact pins in a lock filerequirements.txt carries ranges, because that is what you intend. After a successful install, pip freeze > requirements.lock.txt records what you actually got, transitive dependencies included. The first documents intent; the second makes an evaluator's install reproduce yours.
Interview grill
What does activate actually do?

It edits environment variables for that shell: prepends the venv's script directory to PATH, sets VIRTUAL_ENV, and stashes the old values so deactivate can restore them. There is no process isolation and no containerisation — it is purely name resolution. Which is why you can skip it entirely by invoking .venv/Scripts/python by full path, and why activating in one terminal has no effect on another.

Why not just use Docker and skip venvs?

Different problems. A container pins the OS, the Python build and the system libraries — that is the deployment story, and it is in Phase 12. A venv solves the inner-loop problem: fast iteration, your debugger attached, no rebuild per edit. In practice you want both, with the Dockerfile installing from the same lock file the venv used, so dev and prod resolve identically.

Concept 11

Configuration: three kinds of setting, three homes

Our loader runs in a deliberate order: load_dotenv(), then read YAML, then overlay FINNIE_* environment variables, then inject secrets, then validate. Each step is a layer that can override the one before, which is the standard precedence chain — defaults < file < environment.

Two details worth knowing. load_dotenv does not overwrite a variable already present in the real environment, so a value injected by a container or CI always beats the file — exactly right. And overlay happens before validation, because environment variables are always strings; pydantic coerces "7" to 7 and rejects "99" for a field bounded at 2. Validate last and you get both coercion and checking for free.

Fail fastA bad config raises at startup, loudly, with the offending field named. It must never surface as a confusing NoneType error three modules downstream, forty seconds into a user's conversation. One typed, validated object built once at the boundary is what buys you that.
Interview grill
Why pydantic rather than just returning the dict from yaml.safe_load?

Three things a dict cannot do. Validation: temperature is bounded at 0–2 and chunk_overlap must be smaller than chunk_size, and both are enforced at load time rather than discovered as a weird bug. Coercion: environment overrides arrive as strings and come out typed. And editor support: cfg.rag.top_k autocompletes and type-checks, whereas cfg["rag"]["top_k"] is a typo waiting to happen that fails at runtime, in production, on the one path you did not test.

Why is get_config wrapped in lru_cache?

It makes it a lazily-initialised singleton: the YAML is parsed on first call and every later caller gets the identical object. Without it, a module importing config in a loop re-reads and re-validates the file, and — worse — two parts of the system could observe different configs if the environment changed mid-run. Lazy rather than module-level so that import time does nothing surprising, and tests can call cache_clear() to force a fresh load.

Your .env is gitignored. How does a new developer know what to set?

.env.example, which is committed, lists every variable with a placeholder and a comment on where to get it. It is the schema for the secret file. The loader also fails with a message naming the missing variable and pointing at that file, so the error teaches the fix — an error message is part of the interface.

Concept 12

Packages, modules and why you run from the root

A directory containing __init__.py is a package. When you write from src.rag.retriever import Retriever, Python walks sys.path looking for a src package, then rag inside it, then the retriever module. sys.path[0] is the directory of the script you launched — which is why running python src/web_app/app.py from inside src/web_app/ makes every src. import vanish.

Hence the rule: always run from the project root. pyproject.toml sets pythonpath = ["."] so pytest does the same thing, and no file in this project ever needs a sys.path.append hack. If you find yourself reaching for one, you are in the wrong directory.

The tree is created empty and complete up front, rather than grown as needed. Growing it organically is how you end up with a utils/helpers.py holding nine unrelated functions — and the rubric asks for this exact structure by name.

Interview grill
Walk me through your folder layout and justify one boundary.

core/ holds cross-cutting infrastructure — config, the LLM client, the compliance wrapper — and no domain logic. rag/, data/, agents/ and workflow/ are layers that each depend downward only: workflow knows about agents, agents know about rag and data, and nothing depends back up on workflow.

The boundary I would defend is data/ versus agents/. The market agent could have called yfinance directly. Keeping the fetch-and-cache layer separate means the caching, the fallback ladder and the rate limiting are testable without an LLM in the loop, and the agent becomes a thin thing I can test with a fake feed. One-way dependencies are what make a system testable in pieces.

Concept 13

Logging, and the rule that no print survives

print has no severity, no timestamp, no source module and no off switch. logging gives all four and one place to change the format. When the router misclassifies a tax question in week three, the line you want is:

2026-11-04 18:02:11 | DEBUG    | src.workflow.router | classified -> portfolio (conf 0.41)

Every module takes its logger as get_logger(__name__). Using __name__ names the logger after its module path, which gives you a free hierarchy: logging.getLogger("src.rag").setLevel("WARNING") later silences one subsystem without touching its code.

Three traps this phase defends against:

  • Duplicate handlers. Streamlit re-executes your whole script on every interaction. Call setup_logging() unguarded and you add a handler per click, so lines print twice, then three times. The _CONFIGURED flag is the fix, and there is a test for it.
  • Library noise. At DEBUG, httpx and openai bury your own output in HTTP chatter. Pin them to WARNING.
  • Windows encoding. FileHandler defaults to the system codepage, which raises on an em dash or a rupee sign. Always pass encoding="utf-8".
Enforced, not merely requestedThe ruff T20 rule in pyproject.toml fails the lint on any print inside src/, with exemptions for tests, scripts and the Streamlit app. A convention nothing checks is a convention that decays.
Interview grill
What would you log at each level?

DEBUG for the things I need when something is wrong and nobody can reproduce it: the router's chosen label and confidence, retrieval scores per chunk, cache hit or miss. INFO for normal lifecycle milestones — index loaded with n chunks, request handled in m milliseconds. WARNING for degraded-but-working: a fallback fired, cached data served stale. ERROR for a failed request with the traceback.

And the discipline that matters more than the levels: never log a secret, and never log a user's full portfolio at INFO. Logs get shipped, aggregated and read by people who should not see either.

You have an intermittent bug in production. What in your Phase 0 setup helps?

Module-named loggers mean a line identifies its own origin without guessing. One format string set in config means I can switch the whole system to JSON for log aggregation in one place. A level configurable by environment variable means I can raise verbosity on a running deployment without a code change. And the router's confidence score logged at DEBUG means the single most likely source of weird behaviour — a borderline classification — is already recorded rather than needing to be reproduced.

Concept 14

load_config — step-by-step walkthrough with a real example

Imagine your .env contains OPENAI_API_KEY=sk-abc123 and you have added FINNIE_LLM__TEMPERATURE=0.7 to test a warmer response style. Here is exactly what happens, in order, when load_config() is called for the first time.

StepWhat runsWhat changes
1. load_dotenvload_dotenv(PROJECT_ROOT / ".env")os.environ["OPENAI_API_KEY"] = "sk-abc123" — now live in memory. Existing env vars are NOT overwritten.
2. Read YAMLyaml.safe_load(config.yaml)raw["llm"]["temperature"] = 0.2 (from file, as a Python float)
3. Apply overrides_apply_env_overrides(raw)raw["llm"]["temperature"] = "0.7" (overwritten, now a string — that's fine, Pydantic coerces it)
4. Collect secretsos.environ.get("OPENAI_API_KEY")raw["secrets"] = {"openai_api_key": "sk-abc123", "alpha_vantage_api_key": None}
5. ValidateConfig(**raw)Pydantic coerces "0.7" → 0.7, checks 0.0 ≤ 0.7 ≤ 2.0 ✓, returns a typed Config object

Now imagine FINNIE_LLM__TEMPERATURE=99 instead. Steps 1–4 succeed identically. In step 5, Pydantic coerces "99" → 99.0, then checks 99.0 ≤ 2.0 → ValidationError. The app crashes at startup, loudly, with the field name in the message. That is the right behaviour.

Precedence chain defaults < config.yaml < FINNIE_* env vars < real environment. load_dotenv does NOT overwrite existing env vars, so a value set by CI or a container always wins over the file — exactly right for production.
Interview grill
Why call load_dotenv before reading YAML, not after?

Because step 3 reads from os.environ. If load_dotenv ran after, the FINNIE_* variables from the .env file would not yet be in the environment when _apply_env_overrides scanned it. Order here is not a style choice — it is load-order correctness.

Why inject secrets in step 4 rather than letting the env-override step handle them?

Two reasons. The override step writes into nested config keys; secrets live under raw["secrets"] and are injected as a whole sub-dict, which is cleaner. More importantly, the override step does not validate presence — it just writes if the key exists. Secrets get their own explicit check: if OPENAI_API_KEY is absent or blank, RuntimeError is raised right here with the variable name in the message, not discovered later as a None comparison error buried in the OpenAI client.

What does yaml.safe_load(file) or {} handle?

An empty YAML file. yaml.safe_load on an empty file returns None, not an empty dict. Without the or {}, the subsequent dict operations would raise TypeError: 'NoneType' object is not subscriptable. It is a one-token defensive guard against a valid edge case.

Interview grill
Why are there eleven Pydantic models instead of one flat Config dict?

Each sub-model is a natural grouping with its own validation rules. RAGConfig has a cross-field validator (overlap < chunk_size) that makes no sense on LLMConfig. Splitting them means each validator is local to the section it guards, and the autocomplete scope in an editor is narrow — when I type cfg.rag. I only see RAG fields. A flat dict of thirty keys has no such locality.

What is Config.resolve() for?

YAML stores paths as strings relative to the project root (e.g. cache/market). But Python functions need absolute paths. resolve(p) converts a config-relative path to absolute by joining it with PROJECT_ROOT if it is not already absolute. Without it, every consumer would have to know to prefix the project root, which is the kind of repeated knowledge that rots.

System design questions

The whole-architecture questions that arrive at the end of an interview. Answerable now; sharper once the build is done.

Scale, cost and failure

Interview grill
Walk me through what happens when a user types a question.

The Streamlit callback appends the message to session state and invokes the compiled graph with a thread id. The graph loads checkpointed state, runs the memory node to assemble profile plus windowed history, then the router node classifies intent — keyword fast path first, LLM classification otherwise. A conditional edge dispatches to one agent node, or fans out to several for a cross-domain query. Each agent gathers what it needs — retrieval from FAISS, a quote from the cached market layer, pure-Python metrics — calls the LLM through the rate-limited client, and appends an AgentResult to state. If several ran, a synthesis node merges them. Everything exits through the compliance wrapper, which appends the disclaimer and screens for recommendation language. State is checkpointed and the response streams back with its citations.

This now has ten thousand concurrent users. What breaks first?

The OpenAI rate limits, immediately — and specifically tokens-per-minute before requests-per-minute, because RAG prompts are large. That becomes a higher usage tier plus a request queue with per-user fairness, and it is the first place I would spend engineering effort. Second, Streamlit: it is single-process and session-affine, so it would be replaced by a FastAPI backend with a separate frontend, which also lets me scale the graph workers independently. Third, the in-process FAISS index is duplicated in every worker's memory; at that point it becomes a shared vector service. The market cache moves from local disk to Redis so a quote is fetched once for all users rather than once per worker. Checkpointing moves to Postgres. Notably, none of that changes the graph or the agents — which is the payoff of having put every external dependency behind an interface.

Where does the money go, and how would you cut it?

Cost is roughly proportional to tokens, and the dominant term is retrieved context in the Q&A path plus the router's own classification call. Four levers, cheapest first: the keyword fast path skips the router LLM call for obvious queries; semantic caching returns a stored answer for near-identical questions; tighter retrieval — three well-chosen chunks beat eight mediocre ones on both cost and accuracy; and model tiering, where a small model handles routing and only the final generation uses the larger one. I would instrument tokens per request per node before optimising anything, because guessing which node dominates is how you optimise the wrong one.

How do you know the system is any good? What do you measure?

Layer by layer, because end-to-end vibes are not a metric. Retrieval: a fixed question set with known-correct source documents, scored on recall@k and whether the right chunk makes the top three. Routing: a labelled query set scored as a classification problem, with a confusion matrix — and the diagonal mistakes matter more than the total, since routing a tax question to Q&A degrades gracefully while routing it to the portfolio agent does not. Generation: faithfulness, meaning every claim is traceable to a retrieved chunk, which an LLM-as-judge can grade at scale once calibrated against my own labels. Plus operational numbers — latency percentiles, fallback rate, cache hit rate — and the compliance guard's hit count, which should be zero and is an alarm when it is not.

What is the weakest part of your system, honestly?

The knowledge base. Everything downstream is bounded by it: a hundred articles I curated myself is thin coverage, it reflects my own blind spots, and there is no freshness process — if tax rules change, nothing tells me. The architecture around it is sound and would support ten thousand articles unchanged, but the content is the bottleneck on answer quality today. Second weakest is routing on genuinely ambiguous multi-intent queries; fan-out helps, but the classification confidence threshold is hand-tuned rather than learned from labelled traffic I do not yet have.
